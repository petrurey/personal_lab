Module 01 / discover before integrating

Inventory apps, AD FS dependencies and connectors

  1. Create an inventory with app owner, hosting location, business function, identities, existing authentication, user count, data sensitivity, vendor license, provisioning support and rollback owner. Include one gallery SaaS, one custom OIDC app and one internal web app.
  2. In Defender portal > Cloud apps > Cloud discovery, review discovered apps and filter a test application. Compare activity, risk, compliance and user/device evidence. If no discovery source exists, configure a snapshot report using a supported firewall/proxy log from your own lab; map the log format correctly before import. Do not upload customer traffic.
  3. For AD FS, verify Connect/Health agents and P1/P2, generate a test relying-party sign-in, then open Enterprise apps > Usage & insights > AD FS application migration. Inspect activity, relying parties and readiness tests. Check claim rules, signing/encryption certificates, WIA, custom transformations and non-browser clients. A low-use app is a migration candidate, not automatic proof of compatibility. No AD FS deployment means this branch is not executed.
  4. Under Cloud apps > App connectors, select a supported service you own, review its permission prerequisites, connect using its dedicated admin credentials and confirm status/activity ingestion. Defender app connectors provide API-based visibility/control; they do not register your OIDC client or install application proxy.
  5. Rank one app for migration. Record which identity, assignment and provisioning data will be retained, what the rollback switch is, and who owns the target app account.

Automation / discovery inventory versus telemetry

$next = 'https://graph.microsoft.com/v1.0/servicePrincipals?$select=id,appId,displayName,preferredSingleSignOnMode,appRoleAssignmentRequired'

    $next = $page.'@odata.nextLink'
}

Module 02 / least privilege

Choose SSO and delegate application management

ApproachWhen to choose it / boundary
OIDC / OAuth 2.0Modern custom apps; authorization code + PKCE. ID token establishes a login; access token is for a specific API. Neither implies an app role unless assigned and emitted.
SAMLVendor accepts signed SAML assertions at its ACS endpoint. Map the NameID/attributes it actually expects; manage certificate rollover.
Password-based / linkedPassword vault/injection for supported legacy apps versus a launch link with authentication managed elsewhere. Linked SSO alone is not an Entra authentication/authorization boundary.
Application proxyExpose an internal app with Entra preauthentication and optional backend SSO. Network publication, preauthentication and backend authorization must be tested separately.
  1. For each inventory item record protocol, exact redirect/ACS URLs, logout behavior, vendor roles, required attributes, app owner and provisioning/deprovisioning design. Choose OIDC for the local capstone and SAML for the gallery branch.
  2. Assign the app operator an appropriate app-management role, not Global Administrator. Application Administrator / Cloud Application Administrator can manage apps; consent for Microsoft Graph application permissions requires a suitably privileged role, such as Privileged Role Administrator, and a separate review.
  3. With P1 and an authorized role administrator, open Roles & admins > New custom role. Create APP-ACCESS-LAB Credential Editor containing microsoft.directory/applications/credentials/update. This is a directory administration role, not the Lab.Reader application role.
  4. Assign it to a separate non-admin lab-app-editor at the scope of a disposable app registration, not the directory root. Do not make this test editor an app owner; ownership would mask the role test. Verify that it can manage credentials for the scoped app but not an unrelated app you own.
  5. For a lower-risk companion role, use basic app-property update instead of credential update. Credential management can allow impersonation of the app; never grant it broadly or exercise it against a privileged app.

Module 03 / gallery application

Integrate a gallery SaaS application

Entra ID > Enterprise apps > New application > Microsoft Entra SAML Toolkit
  1. Add the Microsoft Entra SAML Toolkit gallery app (or an owned SaaS test tenant with its current integration tutorial). Name it APP-ACCESS-LAB-SAML. A gallery template provides integration defaults, not completed vendor-side configuration.
  2. Open Single sign-on > SAML. In the toolkit's test configuration, obtain its exact Identifier (Entity ID), Reply URL (ACS) and optional Sign-on URL. Enter those values in Basic SAML Configuration. Do not invent ACS URLs or copy another vendor's settings.
  3. Review Attributes & Claims: choose NameID format and source required by the vendor. Map display name/email only if the test account has the values. Check whether the vendor needs UPN, email, immutable identifier or a specific role claim.
  4. Download the signing certificate/federation metadata and import them into the owned test application. Store the vendor's account credentials securely. Record signing-certificate expiry and a rollover plan; an uploaded certificate alone does not establish trust without the vendor binding.
  5. Set Properties > Assignment required? Yes, leave sign-in enabled, and assign only lab-app-allowed. If the vendor uses local accounts, create/map its allowed-user account or configure provisioning first. Use Test this application and verify the assertion at the owned service.
  6. Compare a signed-in but unassigned non-admin user: the Entra assignment gate should deny the new sign-in. Also test direct vendor login. If local password login still works, document that bypass and disable it only in your owned test SaaS if its design permits.

Automation / instantiate the same gallery template

# Delegated Application.ReadWrite.All + an authorized app-management role.

if ($templates.value.Count -ne 1) { throw 'Resolve the current gallery template ID manually; do not choose an arbitrary match.' }
$templateId = $templates.value[0].id
$body = @{displayName='APP-ACCESS-LAB-SAML'}
Invoke-MgGraphRequest -Method POST -Uri "https://graph.microsoft.com/v1.0/applicationTemplates/$templateId/instantiate" -Body ($body | ConvertTo-Json) -ContentType 'application/json'
# Record returned application and service-principal IDs.
# Vendor-specific SAML claim mapping/certificate setup still follows its integration tutorial.

Graph can automate template instantiation, service-principal assignment and supported claims policies. Vendor-side trust, account mapping and certificate installation need the vendor's own supported API or portal; do not assume template creation finishes SAML SSO.

Module 04 / non-gallery and on-premises

Integrate custom SaaS and publish an internal app

Custom SaaS branch

  1. For a non-gallery SAML application, choose New application > Create your own application > Integrate any other application you don't find in the gallery. Name it with the lab prefix and configure the vendor's Entity ID, ACS, NameID and signing trust as in Module 03.
  2. For a custom OIDC application, use an app registration, not a generic SAML enterprise-app wizard. Its tenant service principal appears under Enterprise apps. Follow Modules 07-09.
  3. If the app supports only password-based SSO, record extension/browser requirements and credential ownership; linked mode is a launch shortcut. Test actual authentication at the app, rather than treating a My Apps tile as access proof.

Application proxy branch / gated

  1. Verify the connector prerequisites from Module 00. On the supported Windows Server, install the Microsoft Entra private network connector using the official installer, register it with the disposable tenant and confirm it is Active in the portal. The connector must reach both the service and the internal web app.
  2. Browse the internal lab application's URL from the connector host. Resolve DNS and TLS trust first. Create a connector group dedicated to the lab if you need isolation; do not place a production connector in it.
  3. Choose Enterprise apps > New application > Add an on-premises application. Enter the reachable internal URL, use the generated external msappproxy.net URL initially, select the lab connector group and choose Microsoft Entra ID preauthentication, not passthrough.
  4. Explicitly grant the new proxy application's delegated User.Read permission admin consent. Since 30 June 2026 new proxy apps no longer receive that consent automatically. Confirm required assignment and assign only the allowed user.
  5. For an anonymous internal test page, demonstrate Entra preauthentication before the page is reachable. For Windows-integrated backend SSO, configure Kerberos constrained delegation, unique SPN, delegation identity and supported user identifier. Domain prerequisites are mandatory; anonymous preauthentication is not proof that KCD works.
  6. Use an external network/browser profile to compare the allowed and denied accounts. A successful connector health check is not sufficient: verify the browser receives the internal test content only after the intended sign-in.

Automation approach

Use the official application-proxy Graph configuration guide and its PowerShell examples for connector/app publication and SSO settings; proxy-specific operations are currently beta. The guide requires a supported app administrator, a preinstalled connector and delegated Directory.ReadWrite.All consent: request that broader permission only for this authorized, disposable branch. Follow its sequence: instantiate custom template, update the application's onPremisesPublishing settings, assign the exact connector group, configure backend SSO, assign the test user, then test the external URL. Export exact lab app/connector-group IDs before changes. Once the proxy service principal exists, the same appRoleAssignmentRequired, user-assignment and delegated-consent Graph operations used by tenant.ps1 apply to that proxy SP. Do not use the capstone SP ID by mistake. Connector installation and AD DS delegation are separate infrastructure operations, not Graph app registration.

Do not expose the capstone loopback server directly to the internet or disable its Host check. Use a separate internal test service for this proxy branch.

Module 05 / provisioning lifecycle

Configure SCIM provisioning with a real target

  1. Select an owned gallery integration that supports provisioning or an owned SCIM 2.0 endpoint. Obtain its provisioning URL and token through the vendor's administrator interface. The supplied OIDC server is not a SCIM service.
  2. Open Enterprise app > Provisioning, select the supported automatic mode, enter the target URL/secret and Test connection. Fix TLS, authentication and supported schema errors before enabling recurring synchronization.
  3. Inspect user mappings. Define a stable source-to-target matching attribute such as userPrincipalName or vendor-supported externalId; verify unique matches and required attributes. Record transformations and how target active state is derived. Do not match only on non-unique display names.
  4. Set scope to Sync only assigned users and groups where supported. Assign the allowed user, use Provision on demand, and verify the account in the target as well as provisioning logs. Check create versus update actions and matching decisions.
  5. Test a source attribute update. Then unassign the allowed user, run the supported provisioning cycle and verify the intended disable/deprovision operation in the target. Record delay and vendor behavior; deletion is not guaranteed by every connector.
  6. Compare the never-assigned denied user: it should not be provisioned by this scoped job. Check for an independently created target account, local login or a second sync job. Assignment, sign-in and target account lifecycle are distinct boundaries.

Automation approach

For supported connectors, use Graph /servicePrincipals/{spId}/synchronization/jobs to inspect/create the connector-specific job and schema, then its /start, /pause or /provisionOnDemand action with the documented payload. Use Synchronization.Read.All for inspection and Synchronization.ReadWrite.All plus a supported administrator role for writes. Resolve the connector's supported template ID first; there is no universal SCIM job template or mapping payload. Save a schema baseline, test one user, then start the recurring job.

# Authenticate with Synchronization.Read.All to the lab tenant.
$SpId = [guid](Read-Host 'Provisioning enterprise app service-principal ID')

$jobs.value | Select-Object id,templateId,schedule,status
# Resolve the exact job, inspect its schema, and follow its connector tutorial before writing.
# Never print provisioning bearer secrets or assume all jobs share a template.

Module 06 / token contracts

Customize claims without confusing consent with access

  1. For the SAML app inspect Attributes & Claims, change one non-sensitive test attribute according to the vendor contract and retest. Record NameID, attribute name/source and signed assertion validation. An attribute visible in the editor is not proof the vendor consumes it.
  2. For the OIDC registration use Token configuration > Add optional claim. Select an appropriate token type, for example email in the ID token, and understand it can be absent or change. Use tenant/object identifiers for internal identity keys; email is not an authorization rule.
  3. Compare tid, aud, issuer, expiry, nonce and roles in locally validated ID-token claims. Treat Graph access tokens as opaque and send them only to Graph; a token intended for your app is not a Graph token. Never paste real tokens into online decoders.
  4. Under Enterprise apps > Consent and permissions, record user-consent policy and admin-consent request workflow. In a disposable branch use a dedicated consent-test app to compare a permitted low-risk delegated permission with one requiring administrator consent. Do not weaken the tenant-wide consent policy to make the capstone work.
  5. For an app requiring assignment, grant administrator consent to its required delegated permissions before end-user sign-in. Assignment itself does not grant consent; consent itself does not assign a user. Check the actual grant record, not just the registration's requested-permissions list.

Automation / optional ID-token claim

# Application.ReadWrite.All; APP-ACCESS-LAB app OBJECT ID only.
$AppObjectId = [guid](Read-Host 'Lab registration object ID')
$body = @{optionalClaims=@{idToken=@(@{name='email';essential=$false})}}
# PATCH replaces the optionalClaims configuration: capture and merge existing claims first.
Invoke-MgGraphRequest -Method PATCH -Uri "https://graph.microsoft.com/v1.0/applications/$AppObjectId" -Body ($body | ConvertTo-Json -Depth 8) -ContentType 'application/json'
# Sign in afresh to inspect new claims; existing tokens do not change.

Use Graph oauth2PermissionGrants to inspect actual delegated grants; granting requested API permissions is separate from configuring requiredResourceAccess. The capstone setup script creates only a User.Read grant for its new client, not a tenant-wide permissive user-consent policy.

Module 07 / application objects

Create the capstone app registration

Entra ID > App registrations > New registration
  1. Register APP-ACCESS-LAB-Web with Accounts in this organizational directory only (AzureADMyOrg). Select Web redirect platform and the exact URI http://localhost:4300/callback. Localhost HTTP is a development exception, not a production hosting pattern.
  2. Record Application (client) ID, Directory (tenant) ID and the registration's Object ID. Find its matching Enterprise application and record that service principal's different Object ID. Graph /applications/{id} takes the registration object ID; assignment calls take the SP object ID; OIDC uses the client ID.
  3. Under Authentication, keep implicit ID/access-token checkboxes off and public-client flows off. This is a confidential web app using authorization code plus PKCE. Do not configure the web redirect as SPA.
  4. Under Certificates & secrets create a short-lived APP-ACCESS-LAB temporary client secret (choose the shortest available portal expiry), copy the value into this terminal's environment and record only its key ID/expiry. The secret ID is not the secret value. Prefer certificate or federated credentials for suitable production workloads; the sample deliberately uses a disposable secret for local teaching.
  5. Set Enterprise-app Properties: Enabled for users to sign-in: Yes, Assignment required: Yes. My Apps visibility may be Yes for discovery, but hiding a tile is not access control. Leave the denied account unassigned.

Module 08 / permissions are resource-specific

Configure delegated, application and multi-tier permissions

  1. On the web registration choose API permissions > Add a permission > Microsoft Graph > Delegated > User.Read. Grant authorized administrator consent for this lab client. Confirm the green consent state and actual grant. Do not add Directory.ReadWrite.All or mailbox permissions to this client.
  2. The signed-in user's Graph /me request uses delegated access and that user's context. A background daemon uses application permissions, app-only consent and client credentials; /me is not available without a user. For planning, identify the exact resource, operation and least-privileged scope/role before requesting consent.
  3. For the multi-tier extension register a separate APP-ACCESS-LAB-API, set an Application ID URI api://API_CLIENT_ID and expose delegated scope access_as_user. Add that scope to the frontend/web client and grant consent. Configure the API's JWT middleware to validate its own audience, issuer, signature, expiry, tenant and required scp value. The supplied web sample is not an API access-token validator.
  4. Have the client request an access token for that API, not Graph, and send it as a Bearer token. Demonstrate that a Graph token cannot be used to call the custom API and that an ID token is not accepted in place of an API token.
  5. If the API needs Graph on behalf of the user, give the API registration delegated Graph User.Read, grant consent, and implement OBO at the API's token endpoint. Exchange the incoming API access token for a new Graph token. Do not forward the incoming token to Graph or use the web client's secret as the API's credential.
  6. For an app-only custom API design expose an application app role (allowed member type Applications), assign it to the caller SP and require roles rather than delegated scp. Document that the User-only Reader role in this capstone does not authorize daemon clients.

Automation / API scope and OBO configuration

# Application.ReadWrite.All; use a NEW disposable API registration.
$ApiObjectId = [guid](Read-Host 'API registration OBJECT ID')
$ApiClientId = [guid](Read-Host 'API application CLIENT ID')
$ScopeId = [guid]::NewGuid().ToString()
$body = @{
    identifierUris=@("api://$ApiClientId")
    api=@{oauth2PermissionScopes=@(@{
        id=$ScopeId;value='access_as_user';type='Admin';isEnabled=$true
        adminConsentDisplayName='Access the lab API';adminConsentDescription='Access the disposable API as the signed-in user'
    })}
}
# This replaces the API scope collection: use only on the NEW lab API.
Invoke-MgGraphRequest -Method PATCH -Uri "https://graph.microsoft.com/v1.0/applications/$ApiObjectId" -Body ($body | ConvertTo-Json -Depth 10) -ContentType 'application/json'
# Add resourceAppId=API client ID + this ScopeId/type=Scope to the caller's
# requiredResourceAccess, preserving its existing Graph entry; consent separately.

OBO's confidential API request uses grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer, requested_token_use=on_behalf_of, the validated incoming assertion and downstream Graph scope. Use a supported token library and the official OBO implementation guide; never log the assertion/secret. This extension requires a separately implemented API; do not claim it ran by merely adding its scope.

Module 09 / authorization

Assign the Reader role to exactly one user

  1. On App registration > App roles > Create app role create Lab Reader, allowed member types Users/Groups, value Lab.Reader, description “Read protected lab content”, Enabled Yes. Create Lab Observer with value Lab.Observer for the later role-only control.
  2. In the matching Enterprise app, confirm Assignment required Yes and sign-in enabled. In Users and groups > Add user/group, assign lab-app-allowed to Lab Reader. Do not assign the denied user, even to Default Access, for the baseline.
  3. Check direct user and group assignments. With P1/P2, a group-based variant may assign Reader to a group containing only the allowed account; nested group membership is not supported. Record group versus direct paths and do not let both paths hide the negative test.
  4. Explain how these controls compose: assignmentRequired gates new sign-in/token issuance; the app validates its login and checks the Lab.Reader role before returning protected content. A frontend hiding a button is not enforcement.
  5. Sign in again after changing roles. Existing tokens/sessions retain their old claims until refreshed/expired, and app assignment changes are not instant global logout. Use the sample's local logout plus a clean browser profile for each comparison.

Module 10 / registration variants

Compare web, SPA and multitenant registration

SPA branch

Module 13 / working application

Start a local OIDC app that enforces its role

  1. Download the six sample files linked at the start, or clone https://github.com/petrurey/personal_lab.git and enter labs\app-access-sample. Node.js 22+ is required. The GitHub Pages site hosts only this guide/source, not the Node server or your secret.
  2. If you used Setup, keep the same PowerShell session so its environment survives; move into the sample folder. If you used the portal, set tenant/client IDs and enter the secret value securely using the block below.
  3. Run npm ci, then npm test, then npm start. Startup performs tenant-specific OIDC discovery. Failures must be fixed before proceeding; there is no “mock success” login mode in the real server.
  4. Open http://localhost:4300, exactly. The server is bound to loopback and rejects other Host headers. Its registered redirect is http://localhost:4300/callback. 127.0.0.1, another port, SPA callback or a trailing-path mismatch is not interchangeable.
  5. Before sign-in, browse /protected and /profile: both return HTTP 401. Sign-in uses authorization code, S256 PKCE, state and nonce checks through openid-client, plus ID-token signature checks. It validates the configured tenant, rotates the server-side session and requires Lab.Reader at both protected routes.
  6. The app keeps secrets/access tokens in server memory only. The browser receives an opaque HttpOnly, SameSite=Lax session ID, not the secret. The local cookie is not Secure because this demonstration uses HTTP localhost; this configuration is not suitable for production. Sessions expire after at most 15 minutes or ID-token expiry.
  7. /logout clears only this application's local session. Use browser profiles/account selection to avoid Microsoft SSO mixing the test users. Stop the server with Ctrl+C and delete its temporary secret during cleanup.

The HTTP test uses a stub identity provider. Module 14 / final scenario

Prove access for one account and denial for another

Use the same app, resource URL, tenant, network and fresh-session conditions for both accounts. Record exact user object IDs so display-name/SSO confusion cannot explain the difference.

  1. Baseline: inspect the web SP: sign-in enabled, assignmentRequired true, only allowed user assigned Lab Reader, no alternative group/direct access for denied. Both accounts are enabled ordinary tenant members. User.Read admin consent is present for this web SP.
  2. Allowed profile: open http://localhost:4300/login, select allowed, satisfy MFA/Conditional Access, and observe the callback then /protected. Expect HTTP 200 with Lab.Reader in the returned claims summary. Request /profile and expect Graph /me for that same allowed account.
  3. Denied profile: start a separate clean profile and choose denied at the same login URL. For an unassigned non-admin user, expect Entra assignment rejection, commonly AADSTS50105. Record the actual code/correlation ID. No protected content or new authorized session may be returned. Do not interpret a password/MFA failure as the desired assignment test.
  4. Role-only control: assign the denied user Lab Observer, not Reader, and sign in fresh. Now authentication can succeed but /protected and /profile must return HTTP 403 for missing Reader. This separates Entra assignment from the app's own role authorization. Remove this Observer assignment afterward to restore the original baseline.
  5. Revocation test: remove allowed's Reader assignment. First observe the existing app session may still work; record its remaining lifetime. Then clear the local session and sign in afresh. Expect the assignment gate to deny. Restore Reader only if more lab testing is needed. Do not claim immediate session revocation from a directory change.
  6. Optional CA control: on a separate, tightly scoped lab policy targeting this app and only the two test users, use report-only MFA first. Interpret sign-in log evaluation, then enforce only after both users are registered and emergency administrators excluded. A CA block is an additional boundary, not evidence of missing app role.
