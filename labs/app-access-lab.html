Configure access for apps

Configure the tenant and application, then test the same resource with an assigned and an unassigned account.

Entra + AzurePortal + automationSeparate knowledge & context

Start here

Core order: 00: tenant → 07: registration → 08: Graph permission → 09: assignment → 13: run app → 14: compare users. Run the licensed extensions before 15: cleanup.

Use a disposable tenant. Technical configuration contains actions and checks. Knowledge & context contains explanations and references, collapsed by default. If an extension's prerequisite is missing, record not run.

Equivalent routes: scripts write the same configuration values as the portal steps. IDs, passwords and certificate bytes are newly generated, not copied between runs. Shared steps are required for both routes. Manual-only means no complete automation alternative is offered; an inventory query is not a replacement.

Automation: use PowerShell 7 and initialize the session in 00. Choose portal or automation for creating the same objects; do not combine creation routes. The scripts refuse existing/unrecorded objects and save only IDs/baselines in the hidden local state file. Never commit that file, secrets or tokens.

Sample downloads: keep package.json, package-lock.json, server.mjs, authorization.mjs, tests and automation.ps1 in one folder.

00 / Core prerequisite

Prepare the tenant and test users

Technical configuration

Required: disposable Entra workforce tenant; User Administrator to create users; Application Administrator or Cloud Application Administrator to manage apps; Node.js 22+, npm and PowerShell 7. Keep an emergency administrator outside lab assignments.

  1. Open Entra admin center. Use the tenant switcher to select the lab directory. Open Entra ID > Overview > Properties; record Tenant ID and primary domain.
  2. Open Entra ID > Users > All users > New user > Create new user. Enter user principal name lab-app-allowed@YOUR_LAB_DOMAIN, display name lab-app-allowed, and Account enabled: Yes. Create the user and retain its temporary password securely.
  3. Repeat for lab-app-denied@YOUR_LAB_DOMAIN / lab-app-denied. Open each user's Overview and record its Object ID.
  4. For both users, open Assigned roles and Groups. Remove any lab-created administrator assignment or app-access group membership; do not use an administrator as a test user.
  5. Sign in as each user in a separate browser profile. Complete the initial password change and any required MFA registration. Leave existing Security Defaults/Conditional Access protections enabled.
  6. Open Users > User settings; record Users can register applications. No change is required when the app administrator creates the registration.
  7. Open Enterprise apps > Consent and permissions > User consent settings; record the existing setting for cleanup. Do not change it for the core scenario.

01 / Licensed extension

Configure discovery and app connectors

Technical configuration

Required: Defender for Cloud Apps. The AD FS subsection requires the separate prerequisites in 00.

Cloud Discovery

  1. Open Defender portal > Cloud Apps > Cloud Discovery.
  2. Select Actions > Create Cloud Discovery snapshot report. Enter APP-ACCESS-LAB-Discovery, select the format matching your lab firewall/proxy, upload that lab's supported log file and select Create.
  3. After processing, select the new report. Filter for a known app present in the uploaded log; record its app name, users/traffic and risk score.

Microsoft 365 app connector

  1. Open Settings > Cloud Apps > Connected apps > App connectors. Select + Connect an app > Microsoft 365.
  2. Use the lab tenant's authorized Microsoft 365 administrator for the connection/consent prompt. Select only the services available in your lab; finish the connection.
  3. Return to App connectors; verify the connection status. Generate a test activity in a selected service and check it in Cloud Apps > Activity log after ingestion.

AD FS app report

  1. Verify Connect Health agents are reporting for the lab AD FS servers. Sign in to one test relying-party application.
  2. Open Entra ID > Enterprise apps > Usage & insights > AD FS application migration. Select the test relying party.
  3. Read its migration status and failing validation checks. Export/record its identifier, reply URL and claims that need changing before migration.
Manual-only — no equivalent script offered for this workflow

The three procedures configure different systems: a Defender snapshot, a consented Microsoft 365 connector and AD FS/Connect Health reporting. The former Graph inventory query did none of these and has been removed. Use the portal/agent steps above. A discovery ingestion API alone would not complete connector authorization or install/report AD FS health agents.

Verify: a discovered app, a healthy connector and/or the AD FS test relying party appears in its respective report.
Knowledge & context

Network discovery finds app usage; Graph inventory lists directory objects. Defender connectors collect SaaS telemetry; private network connectors publish internal apps. AD FS migration reports include active relying parties from the last 30 days, not every historical app.

02 / Licensed extension

Delegate app administration

Technical configuration

Required: Privileged Role Administrator; P1/P2 for the custom role. Create a separate lab-app-editor using 00 and a disposable APP-ACCESS-LAB-AdminScope registration using 07's registration fields.

  1. To authorize the app operator, open Entra ID > Roles & admins > Application Administrator > Add assignments. Select the lab operator, not either access-test user, and add the assignment.
  2. Open Roles & admins > New custom role. Set Name to APP-ACCESS-LAB Credential Editor and select Start from scratch.
  3. On Permissions, search for and select microsoft.directory/applications/credentials/update. Select Review + create > Create.
  4. Open App registrations > APP-ACCESS-LAB-AdminScope > Roles and administrators. Select the new custom role > Add assignments > select lab-app-editor > Add. Do not assign this role at tenant scope.
  5. In the editor's browser profile, open that registration > Certificates & secrets > Client secrets > New client secret. Create a temporary test credential, then delete it without copying its value.
  6. Try the same credential operation on a second lab registration where the editor has no role/ownership. Confirm it is denied.
Automation — assign both administrative roles at the same scopes

Shared prerequisites: create the separate ordinary editor and ensure it has no ownership/admin role. The editor's positive/negative credential tests are the same verification steps 5-6 for either route.

New-LabRegistration -Name 'APP-ACCESS-LAB-AdminScope' | Out-Null
New-LabDirectoryRole -OperatorId (Read-Host 'Lab operator USER GUID') -EditorId (Read-Host 'Editor USER GUID')

Result: Application Administrator assigned to the operator at tenant scope (unless already assigned); the enabled custom credential-update role assigned to the editor only at the AdminScope registration's object scope.

Verify: the editor can update credentials only for the scoped disposable registration.
Knowledge & context

A directory administration role controls who configures apps. An application role such as Lab.Reader controls what a signed-in app user can do. Credential-update permission can enable app impersonation; restrict it to this disposable app.

Use OIDC for modern custom apps, SAML when the SaaS supports assertions, and proxy for internal apps. Password-based SSO needs the supported browser extension; linked SSO is only a launch link.

03 / SAML extension

Configure the gallery SAML Toolkit

Technical configuration

  1. Open Entra ID > Enterprise apps > New application. Search for Microsoft Entra SAML Toolkit, select it, set Name to APP-ACCESS-LAB-SAML and select Create.
  2. Open the app > Properties. Set Enabled for users to sign-in: Yes and Assignment required: Yes; select Save.
  3. Open Users and groups > Add user/group. Select only lab-app-allowed and select Assign.
  4. Open Single sign-on > SAML > Basic SAML Configuration > Edit. Set Reply URL to https://samltoolkit.azurewebsites.net/SAML/Consume and Sign on URL to https://samltoolkit.azurewebsites.net/. Keep the toolkit's generated Identifier (Entity ID); save.
  5. Under Attributes & Claims, verify Unique User Identifier (Name ID) uses user.userprincipalname for this toolkit account.
  6. Under SAML Certificates, download Certificate (Raw). Under Set up, record Login URL, Microsoft Entra Identifier and Logout URL.
  7. Open the toolkit site > Register. Use the allowed user's UPN as its email and create a toolkit-only password. Sign in to that toolkit account.
  8. Open SAML Configuration > Create. Enter the three Entra values from the previous step; upload the raw certificate and select Create. Record the generated SP Initiated Login URL and ACS URL.
  9. Return to Entra > Basic SAML Configuration > Edit. Replace Reply URL with the generated ACS URL and Sign on URL with the generated SP Initiated Login URL; save.
  10. Select Test > Test sign in. Authenticate as the allowed user; confirm the toolkit receives the assertion. Repeat in the denied user's profile and confirm Entra blocks the unassigned account.
Hybrid route — automate Entra configuration, share toolkit registration/trust 
New-LabTemplateApp -Name 'APP-ACCESS-LAB-SAML' -TemplateName 'Microsoft Entra SAML Toolkit' | Out-Null
Set-LabSaml -Name 'APP-ACCESS-LAB-SAML' -ReplyUrl 'https://samltoolkit.azurewebsites.net/SAML/Consume' -SignOnUrl 'https://samltoolkit.azurewebsites.net/'
Add-LabDefaultAssignment -Name 'APP-ACCESS-LAB-SAML' -PrincipalId (Get-LabObject 'lab-app-allowed').id

Shared steps 7-8: register the allowed user's toolkit account and create its vendor-side SAML configuration using the returned login/issuer/logout values and raw certificate file. The toolkit has no supported management API used by this lab.

Set-LabSaml -Name 'APP-ACCESS-LAB-SAML' -ReplyUrl (Read-Host 'Toolkit-generated ACS URL') -SignOnUrl (Read-Host 'Toolkit-generated SP Initiated Login URL')

Result after the shared steps: same gallery app, final ACS/Sign-on URLs, SAML mode/trust, active certificate, required assignment and allowed-only access. Run the same two-user test in step 10.

Verify: allowed reaches the SAML test app; denied fails the assignment gate.
Knowledge & context

The enterprise app issues an assertion; the SaaS must trust the signing certificate and match the NameID to its local account. SSO and local password login are separate paths. Certificate renewal must update the SaaS trust before expiry.

Configure custom SaaS and application proxy

Technical configuration

Non-gallery SAML app

  1. Obtain the owned SaaS tenant's Entity ID, ACS URL, optional Sign-on URL and required NameID/attributes from its administrator.
  2. Open Enterprise apps > New application > Create your own application. Name it APP-ACCESS-LAB-CustomSAML; choose Integrate any other application you don't find in the gallery > Create.

  4. Import Entra's signing certificate and issuer/login values into the SaaS's SAML administrator settings. Set assignment required and assign allowed as in 03; create/map its SaaS account and test.

  3. Select New connector group; name it APP-ACCESS-LAB-Connectors. Select only the new lab connector; save.
  4. From the connector host, browse the internal app's full URL and verify DNS/TLS/reachability.
  5. In Enterprise apps > New application, choose Add an on-premises application. Enter these fields and select Create:

Optional Kerberos backend SSO — same-domain lab

05 / Provisioning extension

Configure user provisioning

Technical configuration

Required: owned SCIM endpoint and token, supported target schema and provisioning entitlements. The Node sample is not a SCIM endpoint.

  1. Open the target's dedicated Enterprise app > Provisioning > Get started. Set Provisioning Mode: Automatic.
  2. Under Admin Credentials, set Tenant URL to the vendor's SCIM base URL and Secret Token to its provisioning bearer token. Select Test Connection; save only after success.
  3. Open Mappings > Provision Microsoft Entra ID Users. Keep provisioning enabled. Verify userPrincipalName → userName is the matching attribute and its matching precedence is 1, unless the vendor's schema explicitly requires another unique key.
  4. Verify required display-name/email mappings against the target schema. Keep the connector's supported active/disable mapping; select Save. Leave group provisioning disabled unless the target supports it.
  5. Open Settings > Scope; select Sync only assigned users and groups. Set failure notification to the lab administrator's address; save.
  6. Under Users and groups, assign only allowed. Open Provision on demand; select allowed > Provision. Confirm a successful create/update in the result and inspect that account in the target.
  7. Return to provisioning > Start provisioning. In Entra, change allowed's display name; use provision on demand again and verify the mapped target update.
  8. Remove allowed's enterprise-app assignment. Let the recurring job process the change; inspect Provisioning logs and confirm the target account's supported disable/deprovision action. Confirm denied was never provisioned by this job.
Manual-only — no complete connector-specific script provided

Use the numbered route above. The removed job-list query did not configure credentials, mappings, assigned-only scope, notification address, assignments or lifecycle changes. The supported synchronization configuration API can automate connector-specific jobs, but this lab does not supply a verified payload for your vendor/schema and all those settings. Do not treat job creation/start alone as an equivalent route.

Verify: create, update and unassignment effects in both provisioning logs and the target account.
Knowledge & context

Provisioning creates/updates target accounts; SSO authenticates users. Removing assignment does not guarantee immediate target deletion: connector mappings, sync timing and vendor behavior determine disable/deprovision results.

06 / Claims and consent extension

Configure token claims and consent requests

Technical configuration

Token configuration — after creating the app in 07

  1. Open App registrations > APP-ACCESS-LAB-Web > Token configuration > Add optional claim.
  2. Select Token type: ID, check email, select Add. If offered, leave the checkbox for adding Graph email permission unchecked; this step adds only the optional ID-token claim.
  3. Open the SAML extension app > Single sign-on > Attributes & Claims > Edit > Add new claim. Set Name: lab_display_name, Source: Attribute, Source attribute: user.displayname; save.
  4. Sign in afresh to the SAML toolkit; inspect the received lab_display_name attribute. For OIDC, inspect the validated claims object with a local server debugger; an optional email may be absent. Do not paste tokens into online decoders.

Admin consent request workflow — disposable tenant only

Required: Global Administrator to enable the workflow. Record these tenant-wide settings before changing them.

  1. Open Enterprise apps > Consent and permissions > User consent settings. For this separate test, select Do not allow user consent; save.
  2. Open Admin consent settings. Set Users can request admin consent to apps they are unable to consent to: Yes.
  3. Under Who can review admin consent requests, add the lab consenting administrator. Set email notifications/reminders to Yes and request expiry to 7 days; save. Allow up to an hour for activation.
  4. Create a separate APP-ACCESS-LAB-Consent client using 07's Web callback http://localhost:4300/callback and a temporary secret. Add delegated Graph User.Read using 08's first step only; do not grant admin consent or enable assignment required for this consent-only test.
  5. Stop the core sample server. Use 13's environment block with the Consent client's ID/secret, then restart the same local sample. Sign in as an ordinary test user and submit the admin approval request.
  6. As the designated reviewer, open Enterprise apps > Admin consent requests > My Pending, select the request, review permissions and approve only this lab client's User.Read request.
  7. Retry sign-in. Consent should now complete; /protected returns 403 because this consent-only client has no Reader assignment. Stop it, restore the core client's environment, and restore the recorded user-consent/workflow settings.

08 / Core permission + API extensions

Configure API permissions

Technical configuration

Core — delegated Graph User.Read

  1. Open App registrations > APP-ACCESS-LAB-Web > API permissions. If User.Read is absent, choose Add a permission > Microsoft Graph > Delegated permissions, search User.Read, check it and select Add permissions.
  2. Select Grant admin consent for YOUR_LAB_TENANT > Yes as an authorized app administrator. Verify User.Read shows Delegated and Granted for YOUR_LAB_TENANT.
  3. In the matching Enterprise app > Permissions, verify the administrator-consented delegated User.Read grant. Continue to 09.

Extension — expose a delegated custom API scope

Required: a separately implemented API with JWT validation. These registration steps do not create an API server.

  1. Register a separate single-tenant APP-ACCESS-LAB-API without a redirect URI. Record its client/object IDs.
  2. Open Expose an API > Add next to Application ID URI. Save api://API_CLIENT_ID, substituting that API's actual client GUID.
  3. Select Add a scope. Set Scope name: access_as_user, Who can consent: Admins only, Admin consent display name: Access the lab API, a matching description, and State: Enabled; add scope.
  4. Create a separate single-tenant APP-ACCESS-LAB-Caller Web registration using your caller implementation's actual redirect; leave its assignment requirement off. On that caller > API permissions > Add a permission > My APIs, select the lab API > Delegated permissions > access_as_user > Add permissions; grant admin consent.
  5. Configure the API middleware with the lab tenant issuer, API audience, signature/expiry checks and required scp=access_as_user. Configure the caller to request api://API_CLIENT_ID/access_as_user; send that access token to the API.
  6. Test a valid API token and rejection of a Graph-audience token or ID token. Use a separate client implementation; the supplied web sample requests Graph User.Read only.

Extension — app-only permission to the custom API

  1. On the API registration > App roles > Create app role, enter display name Lab API Reader, allowed member type Applications, value Lab.Api.Read, description and Enabled Yes.
  2. Register a separate APP-ACCESS-LAB-Daemon without a redirect URI; leave its assignment requirement off. Create a confidential credential with 07's description and custom one-day expiry.
  3. On the daemon > API permissions > Add a permission > My APIs > lab API > Application permissions, select Lab.Api.Read; add and grant admin consent.
  4. Configure the daemon's client-credentials request with the lab tenant, its own client ID/credential and scope api://API_CLIENT_ID/.default. Configure the API to require roles=Lab.Api.Read for app-only requests.
